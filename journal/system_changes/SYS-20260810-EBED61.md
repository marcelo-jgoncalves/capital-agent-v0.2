# System Change: Add differentiated allocation cap for low-risk reserve instruments

- Date/time: 2026-08-10T15:49:42-03:00
- Change ID: SYS-20260810-EBED61
- Change class: C
- Status: IMPLEMENTED_HUMAN_APPROVED

## Problem observed

Tesouro Selic's real minimum purchase lot (BRL 196.64) exceeded the general max_single_live_allocation_pct_equity cap (10%%, BRL 100 at current equity), making the reserve-parking action recommended in DEC-20260810-A032A0 and approved by the human owner impossible to execute. HER-20260810-5961BE was cancelled as a result.

## Evidence

`HER-20260810-5961BE` (BUY Tesouro Selic, BRL 100) was refused by
`policy_check_proposal` when the human owner reported the real minimum lot
(BRL 196.64) — confirmed live before this change. The critical-decision
approval package `approvals/archive/APR-20260810-3DF0B2.md` was prepared
and presented to the human owner *before* any config edit was made, per
`SYSTEM_EVOLUTION.md` Class C ("must be proposed but not activated without
human approval"). Human owner's own words recorded there: "Se você acha que
isso é o melhor para o nosso objetivo, eu aprovo."

## Proposed change

Added max_single_reserve_instrument_pct_equity=0.3 to config/policy.json. policy_check_proposal() now accepts is_reserve_instrument and applies this looser cap only when set; the general cap is unchanged for everything else. request-execution gained an explicit --reserve-instrument flag (an audited, self-declared claim persisted on the execution record as reserve_instrument_claimed, not inferred from the asset name). min_cash_reserve_pct_equity (BRL 500 floor) is untouched.

## Expected benefit

Tesouro Selic (and similarly-sized Tesouro Direto instruments) become executable for reserve parking without weakening the cap that governs actual risky market positions. Human-authorized per APR-20260810-3DF0B2 before any config edit was made, per SYSTEM_EVOLUTION.md Class C.

## New risks introduced

See `approvals/archive/APR-20260810-3DF0B2.md` "Critic assessment" for the
full analysis: the design trusts the requester's honesty about what counts
as a reserve instrument, mitigated by the claim being permanently recorded
and auditable (`reserve_instrument_claimed` on every execution request) and
by the custody invariant meaning misclassification changes only what the
agent recommends, never what actually gets executed.

## Authority impact

Increases what the agent may *recommend* for reserve-flagged purchases
(BRL 100 -> BRL 300 at current equity); does not touch
`min_cash_reserve_pct_equity` or the cap governing risky market positions.
This is exactly the bounded relaxation described and approved in
`APR-20260810-3DF0B2` — no broader authority was taken.

## Rollback plan

Remove `max_single_reserve_instrument_pct_equity` from `config/policy.json`
(the code falls back to the general cap when the field is absent, per the
`"max_single_reserve_instrument_pct_equity" in policy` check) and revert the
`--reserve-instrument` CLI addition. `git revert` this commit achieves both.

## Validation plan

`python -m unittest discover -s tests`; manually confirm a reserve-flagged
BRL 196.64 request is accepted while an unflagged request for the same
amount against the general cap is refused.
