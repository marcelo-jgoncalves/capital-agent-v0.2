# System Change: Close two custody-invariant bypass paths found during Phase 0 readiness audit

- Date/time: 2026-08-10T10:59:52-03:00
- Change ID: SYS-20260810-F9CEAA
- Change class: A
- Status: PROPOSED_AUTONOMOUSLY_ALLOWED

## Problem observed

The Phase 0 readiness audit (journal/reviews/phase0-readiness.md) found two ways an AI operator could accidentally or carelessly cause the ledger to reflect an unexecuted transaction or grant financial write capability without triggering the custody-invariant guard: (1) 'capital_agent.py record --type buy|sell|capital_out' wrote directly to data/ledger.csv with no requirement that a Human Execution Request was ever confirmed by the human, entirely bypassing the execution/ lifecycle added in SYS-20260810-BD6581; (2) 'propose-system-change --enables-autonomous-financial-execution' only forced Class D rejection if the proposer set that flag honestly, with no independent check on the proposal text itself.

## Evidence

Found by direct code reading (`src/capital_agent.py`) during Phase 0
readiness audit item 4/5 ("identify any way an AI could accidentally record
an unexecuted transaction as real" / "identify any way financial write
authority could be enabled without a human gate"). Confirmed live before the
fix: `python src/capital_agent.py record --type buy --category market
--amount 5 --description "sneaky" --reference TEST` succeeded and wrote a
`buy` row to `data/ledger.csv` with no reference to any Human Execution
Request. Confirmed live after the fix: the same command now exits 1 with an
explanation. Also confirmed `grep -n APPROVED src/capital_agent.py` shows the
string is only ever read (`_approval_decision`), never written by any CLI
command, before proposing the keyword-scan change — ruling out a similar gap
on the approval side (a residual, harder limitation of the filesystem-only
trust model is recorded separately in `context/knowledge/open-questions.md`
rather than "fixed," since it has no equally cheap code-level fix).

## Proposed change

(1) Added RECORD_BLOCKED_TYPES = {buy, sell, capital_out} to cmd_record in src/capital_agent.py; these types now refuse with a SystemExit explaining they must go through request-execution/confirm-execution instead. Non-execution bookkeeping types (capital_in, revenue, refund, expense, fee, tax, adjustment) remain available via record. (2) Added a CUSTODY_RISK_KEYWORDS scan over the problem/change/benefit text in cmd_propose_system_change; if a keyword like place_order, broker api, write access, withdraw(, transfer(, buy(, sell( is found without either --enables-autonomous-financial-execution or a new --acknowledge-no-autonomous-financial-execution flag, the proposal is refused rather than silently allowed. Also renamed the unused config/policy.json field human_gate_for_first_live_adapter to human_gate_for_first_readonly_financial_adapter to match the post-custody-invariant architecture (verified unreferenced by any code before renaming).

## Expected benefit

Closes the most direct remaining path by which an AI operator could fabricate a real-looking ledger entry without human confirmation, and adds a second, text-based check that does not rely solely on the proposer's honesty when self-declaring a system change's custody impact. Both fixes are covered by new tests (record: 2 tests; propose-system-change keyword scan: 2 tests) in tests/test_custody_and_execution.py, bringing the suite to 39/39 passing.

## New risks introduced

- The keyword scan is a text heuristic, not semantic understanding: it can be
  triggered by legitimate proposals that merely discuss these terms (as this
  proposal's own text did, requiring
  `--acknowledge-no-autonomous-financial-execution` to proceed) and can in
  principle be evaded by describing the same capability without matching
  keywords. It is deliberately an additional net, not a replacement for the
  `--enables-autonomous-financial-execution` flag or for human review of
  `journal/system_changes/`.
- Blocking `record --type capital_out` means any legitimate non-execution use
  of that type (if one is ever identified) would need a new path. None is
  known today; `capital_out` was only ever used conceptually for
  withdrawals/transfers, which now correctly route through
  `request-execution --action WITHDRAWAL/TRANSFER` instead.

## Authority impact

None in the direction of expanding authority; this strictly narrows what
`record` and `propose-system-change` will silently accept. No hard limit in
`config/policy.json` or `config/critical_decisions.json` changed value.

## Rollback plan

Pre-change state is git commit `a52323c` (the custody-invariant commit this
audit followed). Rollback: `git revert` the commit introducing this change.
Purely additive guards; reverting only restores the two bypass paths, not any
data loss.
