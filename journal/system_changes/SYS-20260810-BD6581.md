# System Change: Custody invariant, Human Execution Request lifecycle, scheduler/orchestration and AI Provider Adapter abstraction

- Date/time: 2026-08-10T10:50:48-03:00
- Change ID: SYS-20260810-BD6581
- Change class: B
- Status: PROPOSED_AUTONOMOUSLY_ALLOWED

## Problem observed

The architecture allowed prose (ARCHITECTURE.md Tier 3/4, execution adapters with execute()/cancel(), HUMAN_GATES Gate H4 'live execution adapter') to describe a future in which the system itself held write authority over real money via broker/exchange adapters. This conflicted with the mandate that custody and financial execution must remain exclusively human. There was also no formal Human Execution Request lifecycle, no scheduler/orchestration system (the AI depended on a human manually starting sessions), and no AI Provider Adapter abstraction separating the Capital Agent from any specific reasoning provider.

## New risks introduced

- A new code surface (`request-execution`/`confirm-execution`/
  `cancel-execution`/`expire-execution`) could, if buggy, let a Human
  Execution Request reach `completed` without genuine human confirmation.
  Mitigated: `cmd_confirm_execution` is the only function that calls
  `append_ledger`, is driven entirely by human-supplied arguments (no
  network/API call), and is covered by
  `tests/test_custody_and_execution.py::HumanExecutionRequestLifecycleTests`
  (11 tests), including that request/cancel/expire/sweep never touch the
  ledger and only confirm does.
- The new `load_policy()` guard raises `RuntimeError` if
  `autonomous_financial_execution_permitted` is ever `true`, which is a
  behavior change for any future code path that tolerates a bad config
  gracefully. Accepted: failing loudly is the correct behavior for a
  corrupted custody-relevant config value.
- `src/scheduler.py` is new unattended-adjacent code (intended to run on an
  external cron); if misconfigured it could queue duplicate or excessive
  jobs. Mitigated: `enqueue()` deduplicates by `job_key` against jobs already
  `queued`, and the scheduler never calls an AI or executes anything itself
  — worst case is redundant job tickets, not incorrect financial state.
- Renamed/repurposed `config/policy.json` fields (`execution_tier`,
  `live_execution_enabled` now mean "operating phase" and "Human Execution
  Requests in active use" rather than implying AI-controlled live trading).
  Mitigated: existing code paths reading these fields were updated
  (`cmd_status`, `build_current_state`), and both old field names are kept
  rather than removed, so no existing caller breaks.

## Authority impact

None in the direction of expanding authority. This change narrows and
hardens the custody boundary: it removes every architectural description of
a future in which the system could hold financial write authority, and adds
enforcement (code guard + forced-rejection CLI flag) that did not exist
before. No file under `config/critical_decisions.json` lowered a threshold;
`config/system_governance.json` gained fields making the custody invariant
more explicit, not less. `config/policy.json`'s new fields
(`autonomous_financial_execution_permitted: false`, etc.) are additive
documentation of an already-true state, not a new capability.

## Result

Implemented and validated. The custody invariant is now stated in every
canonical document that previously touched execution authority, enforced in
code (`load_policy` guard, forced-Class-D flag), and given a concrete,
tested lifecycle (`execution/`). The scheduler and AI Provider Adapter
abstraction exist and are exercised by tests, though only the "manual"
adapter is implemented — an unattended API-driven adapter remains future
work (documented as such in `adapters/ai_providers/README.md`, not
overclaimed).

## Proposed change

Rewrote AI_OPERATING_MANUAL.md, ARCHITECTURE.md, ROADMAP.md, HUMAN_GATES.md, CRITICAL_DECISIONS.md, SYSTEM_EVOLUTION.md, INVESTMENT_POLICY.md, README.md, PHASE0_READINESS_PROMPT.md, START_HERE.md, CLAUDE.md, AGENTS.md, CONTEXT_MANAGEMENT.md, EVALUATION_CRITIC_SYSTEM.md and prompts/weekly_review.md to formalize a custody invariant (only the human owner may access, custody or move real money) as a hard, non-relaxable architectural property. Removed all prose describing autonomous/bounded financial execution, write-capable execution adapters, and execution Tiers 3/4. Added execution/human_requests/{pending,completed,expired,cancelled}/ with a full lifecycle (execution/README.md) and new CLI commands in src/capital_agent.py (request-execution, confirm-execution, cancel-execution, expire-execution, sweep-expired-executions, execution-requests); only confirm-execution, driven by human-reported values, may write to data/ledger.csv. Added a code-level guard (load_policy raising RuntimeError if autonomous_financial_execution_permitted is ever true) and a forced-rejection flag on propose-system-change (--enables-autonomous-financial-execution forces Class D REJECTED_PROHIBITED regardless of requested class). Added config/policy.json fields documenting the invariant, config/schedules.json and config/triggers.json, state/scheduler_state.json and state/pending_jobs.json, src/scheduler.py (deterministic-first job queue, no AI calls, no vendor dependency), scheduler/README.md, and adapters/ai_providers/ (base.py contract, manual_adapter.py reference implementation, README.md) as the AI Provider Adapter abstraction. Updated context/CURRENT_STATE.md generation to include pending Human Execution Requests and never treat a pending or approved item as executed.

## Expected benefit

The architecture now structurally cannot grant the system financial write authority: no code path exists to mark a Human Execution Request completed without an explicit human-reported confirmation, no broker/exchange client library is referenced anywhere in source, and any self-proposed system change claiming to enable autonomous financial execution is auto-rejected as Class D regardless of its requested class. Analytical autonomy (research, decision, sizing, recommendation) remains broad and unblocked. The system can now also operate on a schedule without a human manually starting every session, and the reasoning provider is a swappable adapter rather than a hardcoded dependency.
